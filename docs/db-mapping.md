# Notion DB 마이그레이션 매핑 규칙

- 작성일: 2026-08-20
- 담당: DB 매핑 설계
- 근거 데이터: `schema/new.json` (신 Notion 원본 DB 6개, 속성 86개)
- 상태: **초안** — 구 Notion 스키마 미확보로 3장(대응표)은 미완

---

## 0. 이 문서의 목적

구 Notion의 데이터를 신 Notion으로 옮길 때, **AI 또는 스크립트가 그대로 따를 수 있는 규칙**을 정의한다.
두 Notion의 DB 구조가 1:1로 대응하지 않기 때문에 사람의 판단 없이 실행 가능한 수준까지 규칙을 명시한다.

이 문서를 읽는 대상:
- CURD 기능 구현자 (필요한 타입과 연산 파악)
- QA 담당자 (실제 이관 실행 및 결과 검증)

---

## 1. 전제 조건

작업 설계에 영향을 주는 제약들이다. 규칙의 상당수가 여기서 파생된다.

### 1-1. 이것은 "이전"이 아니라 "병합"이다

신 Notion에는 이미 데이터가 들어가 있다 (회의록 수십 건, 동아리원 18명, 지식 아카이브 20건 이상).
빈 DB에 붓는 것이 아니므로 **중복 방지가 최우선 제약**이다.

### 1-2. 삭제 수단이 없다

현재 CURD 구현 범위와 write skill 모두 delete/archive를 명시적으로 제외하고 있다.
따라서 **잘못 생성된 데이터를 자동으로 되돌릴 수 없다.**

이 문서의 규칙은 전부 "확실하지 않으면 만들지 않는다"를 기본값으로 한다.
애매한 항목은 자동 생성 대신 **보류 목록에 기록하고 사람이 판단**한다.

### 1-3. 두 Notion은 서로 다른 워크스페이스다

- 인증 수단이 각각 필요하다
- **relation은 워크스페이스를 넘지 못한다** → 구 Notion의 relation 값을 그대로 쓸 수 없고, 신 Notion에서 다시 연결해야 한다 (4장 참조)

### 1-4. 이관 범위

> ⚠️ **확인 필요**: 리드가 공지한 범위는 "진행중인 행사 관련 작업 + 신규 멤버 모집 관련 작업"이다.
> 이것이 (a) 구 Notion 전체 중 해당 항목만인지, (b) 1차 범위이고 이후 전체로 확대하는지 확정이 필요하다.
> 범위에 따라 접두어 목록(2-3)과 이관 순서(5장)의 실행 대상이 달라진다.

## 2. legacy_id — 출처 추적 필드

### 2-1. 역할

두 가지 목적을 동시에 수행하는 핵심 인프라 필드다.

1. **중복 방지** — 이미 옮긴 항목을 다시 만들지 않는다
2. **relation 재연결** — 구 페이지 ID로 신 페이지를 역추적한다 (4장)

두 번째 역할 때문에 이 필드는 선택 사항이 아니다. 없으면 relation 24개를 아예 채울 수 없다.

### 2-2. 사양

| 항목 | 값 |
|---|---|
| 속성명 | `legacy_id` |
| 타입 | text |
| 적용 범위 | 신 Notion 원본 DB 6개 전부 |
| 기존 데이터 | 빈 값 유지 (신 Notion에서 직접 생성된 항목은 출처가 없음) |
| 속성 설명 | "데이터 이관용 시스템 필드입니다. 직접 수정하지 마세요." |

### 2-3. 값 형식

```
<출처DB슬러그>:<구 페이지 ID>
```

**구 페이지 ID는 하이픈을 제거한 32자로 통일한다.**
Notion API는 같은 페이지를 `3742463a-9512-8058-...`와 `3742463a95128058...` 두 형태로 반환한다.
정규화하지 않으면 동일 페이지가 서로 다른 `legacy_id`로 저장되어 중복 판정이 깨진다.

예시:
```
meeting:2e43b919cadb80d8ae61c37 49c788cc6
```

**접두어를 붙이는 이유**: 신 Notion의 `업무 캘린더` DB는 구 Notion의 여러 DB를 흡수한다
(회의록 + 행사 일정 등). 접두어가 없으면 이관 후 각 행의 출처를 구분할 수 없고,
"회의록만 재이관" 같은 부분 재실행이 불가능해진다.

> ⚠️ **TBD** — 구 Notion 스키마 확보 후 확정한다.
> 아래는 라이브러리 화면에서 확인된 DB 이름 기준의 잠정안이다.

| 구 DB | 슬러그(안) |
|---|---|
| 회의록 | `meeting` |
| Team Member 연락망 | `member` |
| 주요 연락처 | `contact` |
| 결석계 | `absence` |
| 기획서 아카이브 | `plan` |
| 23-24(전반기) / 23-24 Legacy / 24-25 Legacy | TBD (기수별 분리 여부 결정 필요) |

## 3. DB 대응표

> ⚠️ **미완** — 구 Notion 스키마 확보 후 작성한다.

### 3-1. 확정된 구조적 대응

구 스키마 없이도 확정할 수 있는 항목이다.

| 구 Notion | 신 Notion | 비고 |
|---|---|---|
| 회의록 DB | `업무 캘린더` DB | **고정값 주입**: `유형 = "회의"` |

신 Notion에는 회의록 전용 DB가 없다. 회의록은 `업무 캘린더` DB의 한 항목이며
`유형`(select) 속성이 `회의`인 행으로 구분된다.
`유형`의 선택지는 `업무 일정` / `행사 일정` / `회의` 3개다.

이것이 "1:1 매칭이 아니다"의 대표 사례이며, **여러 구 DB → 하나의 신 DB** 패턴이 다른 곳에도
있을 가능성이 높다. 구 스키마 확보 시 우선적으로 확인할 것.

### 3-2. 나머지 대응

> **TBD** — 구 DB별로 아래 형식을 채운다.

```

```

## 4. 속성 타입별 처리 규칙

신 Notion 6개 DB의 속성 86개를 타입별로 분류한 결과다.

### 4-1. 타입 분포

| 타입 | 개수 | 쓰기 |
|---|---:|---|
| relation | 24 | 2패스 |
| formula | 12 | ❌ |
| text | 10 | ✅ |
| date | 7 | ✅ |
| title | 6 | ✅ |
| select | 5 | ✅ |
| rollup | 4 | ❌ |
| person | 3 | 조건부 |
| multi_select | 3 | ✅ |
| status | 2 | ✅ |
| email | 2 | ✅ |
| url | 2 | ✅ |
| checkbox | 2 | ✅ |
| created_time | 2 | ❌ |
| button | 2 | ❌ |
| **합계** | **86** | |

### 4-2. 이관 제외 속성 (20개)

Notion이 자동 계산하거나 동작을 정의하는 속성으로, **쓰기를 시도하면 안 된다.**

| 타입 | 개수 | 이유 |
|---|---:|---|
| formula | 12 | 수식 계산 결과 |
| rollup | 4 | relation 기반 자동 집계 |
| button | 2 | 동작 정의 |
| created_time | 2 | Notion이 생성 시각 자동 기록 |

**중요**: formula 12개와 rollup 4개는 relation이 올바르게 연결되면 자동으로 채워진다.
즉 **relation 정확도가 곧 이 16개 속성의 정확도**다. 별도로 옮길 필요가 없고, 옮겨서도 안 된다.

실제 이관 대상 속성은 **66개**다.

### 4-3. 타입별 값 형태

| 타입 | 값 형태 | 주의 |
|---|---|---|
| title | 문자열 | DB마다 title 속성명이 다르다 (`이름` / `내용`) |
| text | 문자열 | |
| select | 옵션 이름 문자열 | **기존 옵션에 없는 값이면 실패한다** (4-4 참조) |
| multi_select | 옵션 이름 배열 | 위와 동일 |
| status | 옵션 이름 문자열 | `시작 전` / `진행 중` / `완료` |
| date | `{ start, end? }` | 문자열 하나로 표현 불가. ISO 8601 |
| checkbox | boolean | |
| email / url | 문자열 | 형식 검증 필요 |
| person | Notion 사용자 ID | 구 Notion 사용자와 신 Notion 사용자가 다른 계정일 수 있음 |
| relation | 신 Notion 페이지 ID 배열 | 2패스에서 처리 (5장) |

### 4-4. select 계열 옵션 불일치 처리

구 Notion의 값이 신 Notion의 선택지에 없는 경우가 반드시 발생한다.

> ⚠️ **결정 필요** — 아래 중 하나를 팀에서 정해야 한다.
>
> - **A안**: 신 Notion에 옵션을 자동 추가한다 → 편하지만 오타·구버전 값이 그대로 들어와 선택지가 오염된다
> - **B안**: 매핑 규칙에 값 대응표를 명시하고, 없는 값은 보류 목록으로 보낸다 → 안전하지만 사전 작업이 필요하다
>
> 신 Notion이 리뉴얼하면서 선택지를 정리한 것으로 보이므로 **B안을 권장**한다.
> 특히 `커뮤니티 지식 아카이브`의 `업무 영역`은 옵션이 16개, `관련 행사`는 11개로 세분화되어 있어
> 자동 추가 시 빠르게 오염된다.

### 4-5. person 속성 처리

> ⚠️ **결정 필요** — `업무.담당자`, `동아리원 개인 정보.Notion User`, `커뮤니티 지식 아카이브.작성자` 3개가 해당한다.
>
> 구 Notion과 신 Notion은 다른 워크스페이스이므로 사용자 계정이 동일하지 않을 수 있다.
> 이름 문자열로 매칭할지, 이관 대상에서 제외할지, 수동 처리할지 결정이 필요하다.

## 5. 이관 절차

### 5-1. relation이 2패스를 강제하는 이유

신 Notion의 relation 24개는 DB 간에 순환한다.

```
동아리원 개인 정보 ─┬─→ 프로젝트 ──→ 업무 ──→ 업무 캘린더
                    │       ↑           ↑          │
                    │       └───────────┴──────────┘
                    └─→ 기수 구분 ──→ 프로젝트
```

A를 만들 때 B가 아직 없고, B를 만들 때 A가 필요한 상황이 발생한다.
따라서 한 번의 순회로는 완성할 수 없다.

### 5-2. 절차

**1패스 — 페이지 생성**
- relation을 제외한 속성만 채워서 페이지를 생성한다
- `legacy_id`를 반드시 함께 기록한다
- 제외 속성 20개는 건드리지 않는다

**2패스 — relation 연결**
- `legacy_id`로 (구 페이지 ID → 신 페이지 ID) 대응표를 구성한다
- 구 Notion의 relation이 가리키던 페이지를 대응표로 변환하여 연결한다
- 대응표에 없는 대상은 보류 목록에 기록한다 (범위 밖이거나 아직 안 옮겨진 항목)

**3패스 — 검증**
- formula / rollup 값이 정상적으로 계산되었는지 확인한다
- 보류 목록을 사람이 검토한다

### 5-3. DB 이관 순서

relation 의존 관계를 위상 정렬한 결과다. 이 순서를 지키면 2패스에서 대상을 찾지 못하는 경우가 줄어든다.

| 순서 | DB | 근거 |
|---:|---|---|
| 1 | 커뮤니티 지식 아카이브 | **relation 0개** — 완전 독립 |
| 2 | 기수 구분 | 다른 DB를 참조하지만 참조당하는 쪽이 많음 |
| 3 | 동아리원 개인 정보 | |
| 4 | 프로젝트 | |
| 5 | 업무 | |
| 6 | 업무 캘린더 | 가장 많이 참조하고 참조당함 |

**파일럿은 `커뮤니티 지식 아카이브`로 한다.**
6개 중 유일하게 relation이 없어 다른 DB에 의존하지 않는다.
전체 파이프라인(조회 → 변환 → 생성 → 검증)을 relation 문제 없이 검증할 수 있다.

## 6. 중복 판정

### 6-1. 1차 — legacy_id

`legacy_id`가 일치하는 항목이 이미 있으면 **생성하지 않는다.**
이관을 여러 번 실행해도 결과가 같도록 보장한다.

### 6-2. 2차 — 자연키

신 Notion에 이미 있던 데이터는 `legacy_id`가 비어 있다.
구 Notion의 항목과 실제로는 같은 것일 수 있으므로 (예: 같은 회의) 별도 판정이 필요하다.

> ⚠️ **결정 필요** — DB별 자연키를 정해야 한다. 잠정안:
>
> | DB | 자연키(안) |
> |---|---|
> | 업무 캘린더 | `이름` + `날짜` |
> | 동아리원 개인 정보 | `이메일` |
> | 프로젝트 | `이름` |
> | 커뮤니티 지식 아카이브 | `이름` + `링크` |
> | 업무 | `내용` + `프로젝트` |
> | 기수 구분 | `이름` |

### 6-3. 자연키가 일치할 때

**자동으로 병합하지 않는다.** 보류 목록에 기록하고 사람이 판단한다.

1-2에서 밝힌 대로 삭제 수단이 없으므로, 잘못 병합하면 되돌릴 방법이 없다.
자동 생성으로 인한 중복은 나중에 수동으로 정리할 수 있지만,
잘못된 자동 병합은 원본 데이터를 훼손한다.

## 7. CURD 기능 요구사항

`feat/#1-base-crud` 브랜치 기준으로, 이 문서의 규칙을 실행하려면 아래가 필요하다.

### 7-1. 타입 확장

현재 정의:
```ts
type NotionPropertyValue = string | number | string[] | null
```

이 타입으로 표현할 수 없는 속성이 **36개**다.

| 타입 | 개수 | 필요한 형태 |
|---|---:|---|
| relation | 24 | 페이지 ID 배열 + 단일/복수 제약(`limit`) 구분 |
| date | 7 | `{ start, end? }` 구조 |
| person | 3 | 사용자 ID |
| status | 2 | 옵션 이름 (그룹 개념 포함) |

### 7-2. 쓰기 불가 속성 거부

formula / rollup / button / created_time (20개)에 값을 쓰려는 요청은
서비스 계층에서 차단하는 것이 안전하다.

### 7-3. 소스 열거 기능

현재 read는 `readPage(pageIdOrUrl)` 단건 조회만 있다.
구 Notion의 DB에서 페이지 목록을 순회할 수단(`query_data_source` 또는 `search`)이
서비스 계층에 필요하다.

### 7-4. 복수 워크스페이스

현재 client 인터페이스는 `connect()` 하나로 단일 워크스페이스를 가정한다.
구 Notion 읽기와 신 Notion 쓰기를 한 프로세스에서 수행하려면
워크스페이스별 인증을 분리해야 한다.
