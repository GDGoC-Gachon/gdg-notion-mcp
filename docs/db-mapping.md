# Notion DB 마이그레이션 매핑 규칙

- 최종 수정: 2026-08-21
- 담당: DB 매핑 설계 (2번 작업)
- 근거 데이터
  - 도착지: `schema/new.json` — 신 Notion 원본 DB 6개, 속성 86개
  - 출발지: `old-schema/schema.json` — 구 Notion read 토큰으로 실측, DB 16개
- 상태: **설계 완료 / 실행 대기 (CURD 기능 필요)**

---

## 0. 목적

구 Notion 데이터를 신 Notion으로 옮길 때 **스크립트가 그대로 따를 수 있는 규칙**을 정의한다.
두 Notion의 구조가 1:1로 대응하지 않으므로, 사람의 판단 없이 실행 가능한 수준까지 명시한다.

읽는 대상: CURD 구현자(필요한 타입·연산), QA 담당자(실행 및 검증)

---

## 1. 전제 조건

### 1-1. 이것은 "이전"이 아니라 "병합"이다
신 Notion에는 이미 데이터가 있다. **중복 방지가 최우선 제약**이다.

### 1-2. 삭제 수단이 없다
CURD 구현 범위와 write skill 모두 delete/archive를 제외한다.
잘못 생성된 데이터를 되돌릴 수 없으므로 **"확실하지 않으면 만들지 않는다"** 를 기본값으로 한다.
애매한 항목은 **보류 목록에 기록하고 사람이 판단**한다.

### 1-3. 두 Notion은 서로 다른 워크스페이스다
- 구 Notion은 개인 계정 안의 페이지 트리다. read 전용 integration 토큰으로 접근한다.
- **relation·person 값은 워크스페이스를 넘지 못한다.** 신 Notion에서 다시 연결해야 한다.

### 1-4. 토큰 범위 제한
발급받은 토큰은 워크스페이스 전체 범위다.
`search` API 를 쓰면 GDGoC 와 무관한 개인 자료까지 조회된다(157개 확인).
**반드시 `GDG on Campus Gachon` 페이지(`20023414-5522-802f-9d7a-e6be52bbe8b8`)를
루트로 삼아 하위만 재귀 탐색한다.** 이 방식으로 16개 DB가 수집된다.

### 1-5. 구 Notion 데이터는 계속 늘어난다
회의록 DB에 2026-08-14까지 신규 항목이 쌓이고 있다. 재실행 시 중복이 생기지 않아야 한다.

## 3. legacy_id — 출처 추적 필드

### 3-1. 역할
1. **중복 방지** — 이미 옮긴 항목을 다시 만들지 않는다
2. **relation 재연결** — 구 페이지 ID 로 신 페이지를 역추적한다 (6장)

2번 때문에 선택 사항이 아니다. 없으면 relation 24개를 채울 수 없다.

### 3-2. 사양

| 항목 | 값 |
|---|---|
| 속성명 | `legacy_id` |
| 타입 | text |
| 적용 범위 | 신 Notion 원본 DB 6개 전부 |
| 기존 데이터 | 빈 값 유지 |
| 속성 설명 | "데이터 이관용 시스템 필드입니다. 직접 수정하지 마세요." |

팀 승인 완료.

### 3-3. 값 형식

```
<출처슬러그>:<구 페이지 ID (하이픈 제거 32자)>
```

**하이픈 제거로 통일하는 이유**: Notion API 가 같은 페이지를 두 형태로 반환한다.
정규화하지 않으면 동일 페이지가 서로 다른 값으로 저장되어 중복 판정이 깨진다.

**접두어를 붙이는 이유**: 신 Notion 의 `업무 캘린더`와 `커뮤니티 지식 아카이브`가
각각 여러 출처를 흡수한다. 접두어가 없으면 출처 구분과 부분 재실행이 불가능하다.

### 3-4. 출처 슬러그

| 구 DB | 슬러그 |
|---|---|
| 회의록 DB | `meeting2526` |
| 회의록 아카이빙 | `meeting2425` |
| 회의 | `meeting2324` |
| 문서 허브 | `dochub` |
| Team Member 연락망 | `member` |
| 주요 연락처 | `campus` |
| 마케팅 아카이빙 페이지 | `mkt` |
| 기획서 아카이브 | `plan` |
| 개별 페이지 문서 | `doc` |

회의록만 기수별로 슬러그를 분리한다. 같은 `업무 캘린더`로 들어가므로 구분이 필요하다.

## 4. 대응표

### 4-1. 회의록 3종 → 업무 캘린더

신 Notion 에는 회의록 전용 DB 가 없다. `업무 캘린더`에서 `유형=회의`인 행이 회의록이다.

**세 DB 는 기수별 분리다.** 기수가 바뀔 때마다 새 DB 를 만들어 써서 속성 이름이 제각각이다.

| | 회의 (23) | 회의록 아카이빙 (27) | 회의록 DB (46) |
|---|---|---|---|
| 기수 | 23-24 | 24-25 | 현재 |
| 시기 | 2024.02~05 | 2024.08~2025.02 | 2026 |
| 제목 | `이름` | `제목` | `Name` |
| 날짜 | `이벤트 시간` | **없음** | `Date of Meeting` |
| 참석자 | `참석자` | `참가자` | `참여자` |
| 분류 | `유형` | `태그`, `프로젝트` | `종류` |
| 기타 | `생성자`, `생성 일시` | `생성자` | `불참자(정기회의)` |

**공통 규칙**

```
[구.회의록 3종] → [신.업무 캘린더]

제외 조건:
  - 제목이 비어 있음
  - 제목에 "템플릿" 또는 "리마인드 문서" 포함

고정값:
  유형 = "회의"

공통 대응:
  제목        → 이름
  참석자 계열  → 참가자   (person → relation, 2패스)
  페이지 본문  → 페이지 본문
  출처 DB     → 기수 구분 (relation, 2패스)

제외 속성:
  생성자 / 생성 일시 / 최종 편집자 (Notion 자동 생성)
```

**DB별 개별 규칙**

```
회의록 DB (46건) — 우선 이관
  Date of Meeting → 날짜
  기수 구분 = 현재 기수
  legacy_id = "meeting2526:" + 구 페이지 ID
  주의: Date of Meeting 빈 값 8건, Name 빈 값 3건
        제목 접두 날짜 제거 ("26.08.14 [기획] 9차 정기회의" → "[기획] 9차 정기회의")

회의록 아카이빙 (27건)
  날짜 속성 없음 → 제목 접두에서 추출 ("0829: ..." → 2024-08-29)
                   연도는 프로젝트 시기(2024.08~2025.02)로 판별
                   추출 실패 시 날짜 비우고 보류 목록
  기수 구분 = 24-25
  legacy_id = "meeting2425:" + 구 페이지 ID

회의 (23건)
  이벤트 시간 → 날짜
  기수 구분 = 23-24
  legacy_id = "meeting2324:" + 구 페이지 ID
  주의: 제목 접두 날짜 형식이 다름 ("240215 : ...")
```

**제목 접두 날짜 형식** — 세 DB 를 합치면 형식이 다양하다.

| 형식 | 예 | 출처 |
|---|---|---|
| `YY.MM.DD` | `26.08.14 [기획] 9차 정기회의` | 회의록 DB |
| `YYMMDD` | `260529 [기획] 2차 정기회의` | 회의록 DB |
| `YYYY.MM.DD` | `2026.05.25 [개발 지원] 2차 정기 회의` | 회의록 DB |
| `MMDD` | `0906 정기회의` | 회의록 DB |
| `MMDD:` | `0829: 첫 정기 회의, ...` | 회의록 아카이빙 |
| `YYMMDD :` | `240215 : 솔챌마감 일주일 전` | 회의 |
| 없음 | `사전회의`, `무한콘 : D -1` | 전부 |

날짜 속성이 있는 DB 는 그쪽을 신뢰하고 제목에서는 접두를 **제거**한다.
`회의록 아카이빙`만 제목에서 **추출**한다.

**분류 값 처리 — 버린다**

세 DB 의 분류 체계가 전부 다르다.

| DB | 속성 | 값 |
|---|---|---|
| 회의록 DB | `종류` | 정기회의 / 상시회의 |
| 회의록 아카이빙 | `태그` | 온보딩 / 정기 회의 / 외부 미팅 / 세션 미팅 / 데브렐팀 |
| 회의 | `유형` | 코어 주간 회의 / 짧은 회의 / 외부회의 / 브레인스토밍 |

기수마다 명명이 달라 통합 체계가 없고, 신 Notion 이 `업무 일정`/`행사 일정`/`회의` 로
이미 정리했다. **신 Notion 구조를 따라 `회의`로 통일한다.**

**`회의록 아카이빙`의 `프로젝트` 속성**

값: `Member 모집` / `iOS 연합 스터디` / `Leets 연합 컨퍼런스` / `외대 연합 devfest` /
`Git & Github 새싹세션` / `AI Hands-on` / `Growth Challenge`

신 `업무 캘린더`의 `관련 프로젝트`(relation → 프로젝트 DB)에 대응할 수 있으나,
신 `프로젝트` DB 에 해당 항목이 없으면 연결할 대상이 없다.
**2패스에서 이름 매칭을 시도하고, 실패 시 보류 목록으로 보낸다.**

**유실**
`불참자(정기회의)` — 신 Notion 에 대응 속성 없음. 34건이 비어 있어 실제 데이터는 12건.

**빈 값으로 들어가는 신 속성**
`장소` / `미팅 요약` / `완료` / `생성된 업무` / `점검 Task`

### 4-2. Team Member 연락망 → 동아리원 개인 정보

**구 스키마 (14명, 속성 9개)**

| 속성 | 타입 |
|---|---|
| `Github` | text |
| `SNS (Instagram,...)` | text |
| `생일` | text |
| `역할` | select — Organizer / Team Member / Alumni |
| `이메일 (Google)` | email |
| `이메일 (Notion)` | email |
| `이메일 (Slack)` | email |
| `전화번호` | phone |

**매핑 규칙**

```
[구.Team Member 연락망] → [신.동아리원 개인 정보]

필드 대응:
  제목(이름)       → 이름
  이메일 (Google)  → 이메일
  역할             → 역할        ⚠️ 신규 속성 (승인 대기)

legacy_id: "member:" + 구 페이지 ID
중복 판정: 1차 legacy_id / 2차 이메일
```

**이메일 3종** — Google/Notion/Slack 값이 모두 동일하므로 Google 기준. 나머지는 이관하지 않는다.

**`역할` → `소속 부서` 대응 불가**

```
구.역할:      Organizer / Team Member / Alumni      (직책·상태)
신.소속 부서:  개발 지원 / 기획 & 운영 / 리더진 / 디자인 & 마케팅   (부서)
```

축이 달라 겹치는 값이 없다. 구 Notion 에 부서 정보가 없어 `Team Member` 를
4개 중 무엇으로 넣을지 판단할 근거가 없다.

**제안**: `역할`(select) 속성을 추가해 원본 값을 받고, `소속 부서`는 비워둔 뒤
현 운영진 기준으로 사람이 채운다.

`Alumni` 도 이관한다. 회의록 참여자에 졸업생이 섞여 있어 제외하면 참가자 연결이 빈다.

**유실** ⚠️ 결정 필요
`Github` / `SNS` / `생일` / `전화번호` / `이메일(Notion)` / `이메일(Slack)`

신 `동아리원 개인 정보`는 실데이터 속성이 4개뿐이라 연락처 정보를 담을 자리가 없다.

### 4-3. 문서 허브 → 커뮤니티 지식 아카이브

**구 스키마 (23행, 속성 12개)**

| 속성 | 타입 | 빈 값 | 값 |
|---|---|---:|---|
| `문서 이름` | title | 0 | |
| `상태` | status | 0 | 시작 전 / 수정 필요 / 진행 중 / 완료 |

  Writing      → (대응 없음)
  Github       → (대응 없음)

**`카테고리` 값 대부분이 신 `업무 영역` 옵션에 없다.** 4-6 방침 적용 → 보류 목록.
단 빈 값이 12건이라 실제 영향은 11건.

| **합계** | **86** | |

### 5-2. 이관 제외 속성 (20개)

Notion 이 자동 계산하거나 동작을 정의하는 속성으로 **쓰기를 시도하면 안 된다.**

| 타입 | 개수 | 이유 |
|---|---:|---|
| formula | 12 | 수식 계산 결과 |
| rollup | 4 | relation 기반 자동 집계 |
| button | 2 | 동작 정의 |
| created_time | 2 | Notion 이 자동 기록 |

formula 12개와 rollup 4개는 relation 이 올바르게 연결되면 자동으로 채워진다.
**relation 정확도가 곧 이 16개의 정확도**이며, 별도로 옮길 필요가 없다.

실제 이관 대상 속성은 **66개**다.

### 5-3. 타입 변환

| 구 → 신 | 처리 |
|---|---|
| date → date | 변환 없음 |
| text / email → 동일 | 변환 없음 |
| **phone → text** | 문자열로 변환 (신 `연락처`가 text) |
| **person → relation** | 표시 이름 매칭, 2패스 (5-4) |
| **select → multi_select** | 단일 값을 배열로 감싼다 |
| **select → status** | 값 대응표 필요 |

### 5-4. 참석자 이름 매칭 (person → relation)

구 Notion 은 Notion 사용자 태그, 신 `참가자`는 `동아리원 개인 정보` relation 이다.
워크스페이스가 달라 자동 변환이 불가능하므로 **표시 이름으로 매칭**한다.

```
1. 정확히 일치하면 연결
2. "/" 포함 시 뒤쪽만 사용         ("루카/최선규" → "최선규")
3. 공백 제거 후 글자 재배열 일치    ("세은 현" → "현세은")
4. 그래도 실패하면 보류 목록        ("Hyeon", "(이름없음)")
```

연락망 인원이 14명으로 적어 실패분은 사람이 판단하면 된다.
**추측으로 자동 연결하지 않는다.** 매칭 실패 시 해당 참가자만 비우고 페이지는 생성한다.

`(이름없음)` 값이 실제로 존재한다(계정 삭제 등). 이 경우는 무조건 보류 목록.

### 5-5. select 옵션 불일치 — B안 채택

구 값이 신 선택지에 없는 경우가 다수 발생한다.

| 사례 | 구 값 | 신 옵션 |
|---|---|---|
| 회의 분류 3종 | 정기회의 / 외부 미팅 / 코어 주간 회의 등 | ❌ |
| 연락망 `역할` | Organizer / Team Member / Alumni | ❌ |
| 문서 허브 `카테고리` | Writing / Github / AI / DevRel 등 | 일부만 |
| 마케팅 `목적 기준 분류` | Archived / Area / Backloged | ❌ |

**옵션을 자동 추가하지 않는다.** 신 Notion 이 리뉴얼하며 선택지를 정리했으므로
임의 추가는 그 구조를 훼손한다.
매핑 규칙에 명시된 값만 변환하고, 없는 값은 **비운 뒤 보류 목록에 기록**한다.

### 5-6. person 속성 ⚠️ 결정 필요

`업무.담당자`, `동아리원 개인 정보.Notion User`, `커뮤니티 지식 아카이브.작성자` 3개.
워크스페이스가 달라 계정이 동일하지 않다. 이름 매칭 / 제외 / 수동 처리 중 결정이 필요하다.

## 6. 이관 절차

### 6-1. relation 이 2패스를 강제하는 이유

신 Notion 의 relation 24개는 DB 간에 순환한다.

```
동아리원 개인 정보 ─┬─→ 프로젝트 ──→ 업무 ──→ 업무 캘린더
                    │       ↑           ↑          │
                    │       └───────────┴──────────┘
                    └─→ 기수 구분 ──→ 프로젝트
```

A 를 만들 때 B 가 없고 B 를 만들 때 A 가 필요한 상황이 발생한다.

### 6-2. 절차

**1패스 — 페이지 생성**
- relation 을 제외한 속성만 채워 페이지를 생성한다
- `legacy_id` 를 반드시 함께 기록한다
- 제외 속성 20개는 건드리지 않는다

**2패스 — relation 연결**
- `legacy_id` 로 (구 페이지 ID → 신 페이지 ID) 대응표를 구성한다
- 참가자·기수 구분·관련 회의록 등을 대응표로 변환하여 연결한다
- 대응표에 없는 대상은 보류 목록에 기록한다

**3패스 — 검증**
- formula / rollup 값이 정상 계산되었는지 확인한다
- 보류 목록을 사람이 검토한다

### 6-3. 이관 순서

| 순서 | 작업 | 행 | 근거 |
|---:|---|---:|---|
| 1 | 주요 연락처 → 아카이브 | 5 | **파일럿**. relation 없음, 소량 |
| 2 | 마케팅 아카이빙 → 아카이브 | 4 | relation 없음 |
| 3 | 기획서 아카이브 → 아카이브 | 3 | relation 없음 |
| 4 | Team Member 연락망 → 동아리원 | 14 | 참가자 매칭의 기준 |

| 6 | 문서 허브 → 아카이브 | 23 | 관련 회의록이 5번 참조 |

## 8. 중복 판정

### 8-1. 1차 — legacy_id
`legacy_id` 가 일치하는 항목이 이미 있으면 **생성하지 않는다.**
이관을 여러 번 실행해도 결과가 같도록 보장한다.

### 8-2. 2차 — 자연키
신 Notion 에 이미 있던 데이터는 `legacy_id` 가 비어 있다.

| 신 DB | 자연키 |
|---|---|
| 업무 캘린더 | `이름` + `날짜` |
| 동아리원 개인 정보 | `이메일` |
| 커뮤니티 지식 아카이브 | `이름` |

### 8-3. 자연키가 일치할 때
**자동으로 병합하지 않는다.** 보류 목록에 기록하고 사람이 판단한다.

삭제 수단이 없으므로(1-2), 중복은 나중에 수동 정리가 가능하지만
잘못된 자동 병합은 원본 데이터를 훼손한다.

## 9. CURD 기능 요구사항

`feat/#1-base-crud` 브랜치 기준으로, 이 문서의 규칙을 실행하려면 아래가 필요하다.

### 9-1. 타입 확장
현재 정의로는 **36개 속성**을 표현할 수 없다.

```ts
type NotionPropertyValue = string | number | string[] | null
```

| 타입 | 개수 | 필요한 형태 |
|---|---:|---|
| relation | 24 | 페이지 ID 배열 + 단일/복수 제약(`limit`) 구분 |
| date | 7 | `{ start, end? }` 구조 |
| person | 3 | 사용자 ID |
| status | 2 | 옵션 이름 (그룹 개념 포함) |

### 9-2. 쓰기 불가 속성 거부
formula / rollup / button / created_time (20개) 쓰기 요청은 서비스 계층에서 차단한다.

### 9-3. 소스 열거 기능
현재 read 는 `readPage(pageIdOrUrl)` 단건 조회뿐이다.
DB 행 목록을 순회할 수단(`query_data_source` 또는 `search`)이 필요하다.

### 9-4. 복수 워크스페이스
client 인터페이스가 `connect()` 하나로 단일 워크스페이스를 가정한다.
구 Notion 읽기와 신 Notion 쓰기를 한 프로세스에서 수행하려면 인증 분리가 필요하다.

### 9-5. Notion API 버전
구 Notion 일부 DB 는 신규 멀티 데이터소스 구조라 `2022-06-28` 로 조회되지 않는다.
`2025-09-03` 이상에서 `/data_sources/{id}` 경로로 접근해야 한다.
